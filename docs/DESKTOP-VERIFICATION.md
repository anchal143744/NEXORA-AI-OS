Moving/removing the folder breaks the shortcut; run `npm run desktop:prepare` after source updates. Logs are in `.local/desktop-server.log`.

## Changes in this increment

- Native hidden-console launcher and branded splash: `scripts/desktop/NexoraLauncher.cs`, `install-desktop.ps1`, `stop-desktop.ps1`; logo sources in `assets/nexora-logo.svg` and `apps/web/app/icon.svg`.
- `scripts/desktop-launch.mjs` validates local-only configuration, authenticates a read-only schema check, starts only the ownership-marked local database when needed, verifies readiness, and reuses owned services. `scripts/dev-start.mjs --desktop` starts compiled builds without watchers or artifact cleanup. Both app ports bind to 127.0.0.1 in desktop mode; production startup behavior is preserved in `apps/api/src/main.ts`.
- `scripts/desktop-backup.mjs` and `scripts/desktop/protect-backup.ps1` create an encrypted daily PostgreSQL custom-dump backup under `.local/backups`. Windows CurrentUser DPAPI protects the file; a SHA-256 manifest validates reuse. Temporary plaintext dumps are removed. These backups require the same Windows user's encryption keys, are on the same disk, and do not replace off-device disaster recovery. A backup failure is reported and does not reset or block the application.
- API overview queries now check CRM, sales, inventory and finance permissions independently. Denied resource fields are omitted; activity is filtered. Frontend queries, navigation, widgets and stale report props follow those permissions (`shop.service.ts`, shop workspace/overview/charts/types). Stock-only roles can use authorized inventory widgets without receiving financial or CRM records.
- `tests/retail.integration.mjs`, `tests/shop-identity.test.mjs`, and `tests/desktop-backup.integration.mjs` verify these boundaries. `scripts/run-retail-tests.mjs` runs restore checks only in its newly created disposable PostgreSQL cluster.

## Remaining limits and next step

The verified retail workflow is available through one local URL. Preserved enterprise modules are not all implemented or audited: real mail delivery/recovery, full purchasing/payables, invitations, advanced automations, live AI actions and forecasts remain outside this delivered retail scope. Real mail providers still fail closed until a transport and user-provided credentials are configured. Fine-grained action-button hiding and the broader legacy API need further review; server permissions continue to enforce authorized actions. This is not a 100% production-readiness claim.

Automatic browser security review blocked local browser visual/click-through verification even after approval. No bypass was attempted. Launcher verification did not open a browser, so native splash interaction and Edge app-window rendering are not verified. The smallest next acceptance step is a user-operated desktop launch and signup/setup/dashboard walkthrough; the next implementation step is a real configured mail transport with delivery and recovery tests. Hosted release additionally needs deployment/TLS, off-device backups, monitoring/recovery and a security review.

Earlier failing-test classifications and the historical repair decisions remain in [retail failure triage](RETAIL-FAILURE-TRIAGE.md). During desktop verification, a native child-process test runner stalled on inherited output handles after the launcher itself succeeded; the exact test helper was stopped and rerun with ignored native output handles. Cold-start then passed. The first loopback-binding build also rejected an optional hostname through a TypeScript overload; explicit branches corrected the call and the subsequent API build and full type checks passed. No tests were disabled to resolve these setup/build failures.
