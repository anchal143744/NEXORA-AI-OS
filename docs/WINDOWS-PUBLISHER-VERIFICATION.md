Microsoft documents trusted-provider code signing as the supported solution. Smart App Control does not provide a per-app allow exception. See [Microsoft's developer signing guidance](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control) and [Smart App Control FAQ](https://support.microsoft.com/en-us/windows/security/threat-malware-protection/smart-app-control-frequently-asked-questions).

**The existing EXE remains blocked/unsigned.** It was not executed, replaced, renamed to evade checks, whitelisted or represented as repaired. A verified publisher certificate and signing key, or a configured trusted signing service, are external prerequisites. A self-signed certificate would not establish a trusted public publisher. Successful signature creation, signed NEXORA launch and Smart App Control acceptance cannot be tested without that prerequisite.

## Changes made

- `scripts/desktop/publisher-signing.ps1`: checks certificate validity, private-key availability, code-signing EKU, trusted chain/revocation, SHA-256 Authenticode signing and trusted timestamp; verifies the final binary and expected signer. Signing keys stay in the Windows certificate store. The helper imports the security module belonging to the current PowerShell host to avoid cross-version module loading.
- `scripts/desktop/install-desktop.ps1`: release builds require signing prerequisites before compilation. It stages a build separately, signs/verifies it before promotion, preserves the previous executable and leaves browser profiles intact. It installs no unsigned shortcuts. Explicit development compilation requires `-NoInstall -DevelopmentBuild`, writes only to a unique `.local/desktop-builds/` folder, and does not execute its output.
- `scripts/desktop/check-signing-readiness.ps1` and `check-desktop-trust.ps1`: read-only, actionable readiness/signature checks. They return failure while signing or publisher verification is missing.
- `package.json`: adds `desktop:signing:check` and `desktop:trust`; `desktop:prepare` checks signing readiness before rebuilding application artifacts. Release prepare/install no longer request an execution-policy bypass. No system execution policy, Smart App Control, Defender settings/exclusions or certificate trust stores were changed.
- `tests/desktop-publisher.integration.mjs`: tests rejection and preservation behavior against actual Windows processes. Existing Git changes and modules were retained. No business schema or transaction code changed.

Once a trusted signing provider has issued the publisher certificate and made its key available in the Windows personal certificate store, set **process environment** `NEXORA_SIGNING_CERT_THUMBPRINT` and `NEXORA_SIGNING_TIMESTAMP_URL` using that provider's actual thumbprint and HTTPS timestamp endpoint. Then run `npm run desktop:signing:check`, `npm run desktop:prepare`, `npm run desktop:trust`, and `npm run desktop:install`. These values are not loaded from .env by the PowerShell signing commands. No example identity, password or timestamp endpoint was invented. The certificate-store path is implemented; a remote/cloud signing-service adapter is not configured or tested.
